## 1. 목적

국내 회사 구매·개발 담당자가 전자부품 품번을 검색해 정식 유통사의 가격·재고를 확인하고,
필요하면 견적 문의 또는 브로커 소싱 문의를 남기게 한다.
이 MVP의 목적은 기능 완성이 아니라 **수요 검증 데이터 수집**이다.

## 2. 범위

### 포함 (MVP)
- 품번(MPN) 검색 → 소스별 결과 표시
- 문의 접수 시 운영자 이메일 알림
- 문의 폼 2종: 견적 문의 / 브로커 소싱 문의 (폼과 저장 데이터 모두 분리)
- 검색 로그·문의 데이터 저장, 간단한 관리자 목록 화면

### 제외 (구현하지 말 것)
- BOM 업로드·매칭, 총비용 최적화, 품의 자료 출력
- 회원가입·로그인 (관리자 화면만 단순 인증)
- 결제, 주문 대행
- Slack 등 이메일 외 알림 채널

## 3. 제약 (반드시 지킬 것)

1. **데이터 수집 방법은 제한하지 않되, 수집 가드레일을 지킨다.**
   - 허용 방법: 공식 API, 공개 웹페이지 수집(스크래핑), 제휴·데이터 피드, 공급처 재고 리스트(CSV/엑셀) 업로드.
   - 수집 가드레일 (공개 웹페이지 수집 시):
     - 로그인·회원 전용 영역은 수집하지 않는다.
     - CAPTCHA 풀이, 봇 차단 우회(프록시 로테이션, 브라우저 지문 위장, 차단 회피 재시도 등) 코드는 작성하지 않는다. 차단·CAPTCHA 응답을 받으면 해당 소스는 "일시 조회 불가"로 처리하고 쿨다운한다.
     - robots.txt에서 금지한 경로는 수집하지 않는다.
     - 소스별 최소 요청 간격과 일일 상한을 둔다 (값은 소스별 설정, 기본은 보수적으로).
     - 검색 시점 조회(on-demand)만 한다. 사이트 전체를 미리 긁어 오는 대량 수집은 하지 않는다.
     - `TODO(확인필요)`: 소스별 이용약관 검토 결과. 약관상 자동 수집을 금지한 소스는 법무 확인 전까지 플래그 off.
2. **소스 연동은 Provider 어댑터 구조로 만들고, 기본값은 비활성(feature flag off)이다.**
   - DigiKey: 외부 사이트 표시 사전 승인 전까지 프로덕션에서 활성화 금지. 승인 회신 후 플래그를 켠다.
   - Mouser: 호출 한도(분당 30회, 하루 1,000회)를 넘지 않도록 Provider별 rate limiter와 일일 쿼터 카운터를 둔다. 한도 도달 시 해당 Provider 결과만 "일시 조회 불가"로 표시하고 나머지는 정상 동작.
   - 웹페이지 수집 Provider도 같은 rate limiter·일일 쿼터 구조를 쓴다.
   - 개발·테스트는 mock Provider와 fixture(JSON, 저장된 HTML)로 진행한다. 실제 API 키는 저장소에 넣지 않는다(.env, 예시는 .env.example).
3. **캐시**: 응답 캐시는 짧은 TTL(기본 15분, 환경변수로 조정)만 허용한다. 수집한 데이터로 장기 보관용 부품 DB를 만들지 않는다. (공급처가 직접 제공한 재고 리스트는 예외: 제공 시 합의한 기간만 보관.) `TODO(확인필요): 소스별 캐시 허용 범위`
4. **출처 표기**: 모든 가격·재고 데이터에 소스명, 조회 시각, 해당 소스 상품 페이지 링크를 붙인다. 서로 다른 소스 데이터를 출처 구분 없이 합치지 않는다. 소스와 제휴·보증 관계가 있는 것처럼 보이는 문구나 로고 사용 금지.
5. **소스 분류와 중립성**:
   - 각 Provider는 `authorized`(정식 유통사) 또는 `broker`(브로커·시장 재고) 중 하나로 분류한다. 분류 기준은 `TODO(확인필요)` (예: LCSC는 브랜드별로 정식 여부가 다름).
   - 정식 유통사 결과(A)에는 `authorized`만 표시하고, `broker` 결과는 섞지 않는다.
   - 정식 유통사 결과는 가격 순 정렬 외에 어떤 가중치나 숨김도 두지 않는다. 문의 유도 요소가 정식 유통사 결과를 가리거나 순서를 바꾸면 안 된다.

## 4. 화면

### 4.1 검색 (`/`)
- 품번 입력창 + 수량 입력(선택). 검색어는 원본 그대로 보존하고, 비교용으로만 대문자·공백 제거 정규화.

### 4.2 결과 (`/search?q=...&qty=...`)
화면을 영역별로 명확히 분리한다.

**A. 정식 유통사 결과**
- Provider별 행: 유통사명, 제조사, 제조사 품번, 설명, 재고, 가격 구간(수량별 단가), MOQ, 통화, 조회 시각, 상품 링크
- 수량 입력 시 해당 수량 기준 단가·합계 표시
- 결과 없음 / Provider 조회 실패를 구분해 표시

**B. 견적 문의**
- 항상 노출. "이 부품의 견적을 받아보세요" 수준의 중립적 문구.

**C. 브로커 소싱 문의**
- 시각적으로 A와 분리된 별도 박스.
- 다음 중 하나면 강조 표시: 검색 결과 없음 / 모든 Provider 재고 0 / 입력 수량 > 최대 재고 / 단종·NRND 상태
- 고지 문구 필수: "브로커 소싱은 정식 유통 경로가 아니며, 정품 보증·반품 조건이 정식 유통사와 다릅니다."

**D. 브로커·시장 재고 (`broker` 소스)** — `TODO(확인필요)`
- 표시 여부와 위치 미정. 후보: (1) 화면에 표시하지 않고 운영자 소싱 참고용으로만 저장·관리자 화면에 노출, (2) C 영역 안에 "시장 재고 참고" 형태로 표시 (가격 비공개, 재고 유무만).
- 표시하는 경우에도 A와 분리하고, C의 고지 문구를 함께 노출한다.

### 4.3 품번 페이지 (`/part/[MPN]`) — SEO·AEO 색인 대상

- 결정 (2026-10-01): (a) 우리 콘텐츠로 구성. 가격·재고는 접속 시 실시간 조회(짧은 TTL 캐시)만 하고 저장하지 않는다.
- URL: 정규화 품번(대문자·공백 제거, URL 인코딩). 비정규 URL은 308로 정규 URL에 이동. canonical 지정.
- 본문 첫 문단은 결론 먼저(제조사·품번·재고 현황·조회 시각·출처). 이어서 A/B/C 영역, 자주 묻는 질문(재고/가격/단종 여부/견적 방법).
- 요약·FAQ 수치는 정식 유통사(authorized) 결과에서만 만든다. broker 결과는 요약에 쓰지 않는다.
- 정식 유통사 결과가 없는 품번은 `noindex, follow`.
- 구조화 데이터: Organization, WebSite(SearchAction), Product(offers 없음), BreadcrumbList, FAQPage.
- `/search` 는 `noindex, follow`. `robots.txt`, `sitemap.xml`(TODO: DB 연결 후 인기 품번 자동 생성), `llms.txt` 제공.
- 브로커 결과 표시 (결정 2026-10-01): 소싱 박스(C) 안 "시장 재고 참고"에 소스명·게시 수량·조회 시각·출처 링크. 가격 비표시.

## 6. 알림 (이메일)

- 문의 접수 시 운영자에게 이메일을 보낸다. 수신 주소는 환경변수로 두고, 견적 문의와 소싱 문의의 수신 주소를 각각 지정할 수 있게 한다(같은 주소여도 됨).
- 수신자는 운영자(우리)로 한정한다. 브로커 등 제3자에게 자동 발송하지 않는다.
- 발송은 트랜잭션 메일 서비스 API(예: AWS SES, Resend)를 통해 하고, 어댑터로 감싸 교체 가능하게 한다. 사용 서비스는 `TODO(확인필요)`. 개발 환경은 콘솔 출력 또는 로컬 메일 캡처로 대체.
- 제목: `[견적 문의] {품번} x {수량}` / `[소싱 문의] {품번} x {수량}` (메일함 필터링용으로 접두어 고정)
- 본문: 문의 종류, 품번, 수량, 희망 납기, 품목 수, 구매 용도, 회사명, 담당자명, 접수 시각, 관리자 화면 링크.
  연락처·이메일 주소는 본문에 넣지 않고 관리자 화면에서만 확인한다.
- 발송 실패해도 문의 저장은 성공해야 한다. 실패는 로그로 남기고 재시도 1회, 관리자 화면에 발송 실패 건 표시.
